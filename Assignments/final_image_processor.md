# Sleep Lab Monitoring Client/Server Project

## Overview
The final project in this class will require you to leverage the
industry-standard skills you've learned during this semester to design
and implement a Sleep Lab Monitoring
System that has a patient-side client, a monitoring-station client, and a
server that allows patient data to be uploaded and stored in a persistent 
database, retrieved for ad-hoc and continuous monitoring, and for communication
between the two clients.

It is expected that you will follow proper professional software
development and design conventions taught in this class, including:
* git feature-branch workflow
* continuous integration
* unit testing
* PEP8
* docstrings
* use of issues and milestones to track development progress (new to this 
assignment)
  
## Functional Specifications
### Patient-side GUI Client
The patient-side GUI client will act as a stand-in for a CPAP machine which is 
tracking a particular patient undergoing a sleep study.  

A package called
`mockcpap` with a class called `MockCPAP` provided simulated flow vs. time
data as would be generated by a CPAP machine.  A patient medical record number
and pressure are sent to this `MockCPAP` class and then subsequent calls to 
a method will give the latest time and flow data from the patient that will be
a function of the MRN and pressure.  The operating pressure of the CPAP can
be modified during data acquisition.  See the provided `mockCPAP` API in the
assignment repository for details on its usage.

At a minimum, your patient-side GUI client should provide a __graphical__ user 
interface with the following functionality:
+ Allow the user to enter a patient name.
+ Allow the user to enter a patient medical record number (MRN).  The MRN
  should be a positive whole number.
+ Allow the user to enter a room number.  The room number should be a positive
  whole number.
+ Allow the user to enter a CPAP pressure in units of cmH2O (the GUI should validate
  that the entry is an integer and must be between 4 and 25, inclusive, which 
  is the typical range for CPAP operation).
+ When all of the information above is entered into the GUI, the user should
  be able to start data acquisition.  This should only be allowed if all of 
  the entered data is correct and validated.  When data acquisition is started:
  + The MockCPAP class should be started.
  + The room number, MRN, patient name, and current CPAP pressure should be
    uploaded to the server via RESTful API request.
  + The entries for room number, medical record number, and patient name 
    should be deactivated so that no changes can be made to them (until the 
    reset as described below).  But, they should still remain visible.
+ After data acquisition is started, at least once every five seconds a 
  plot of flow versus time should be displayed and updated with the latest data.  
  Only the latest 60 seconds worth of data should be shown.
+ After the first 60 seconds of data is obtained, the breathing rate and the
  number of apnea events should be calculated from the latest 60 seconds of
  data.  The breathing rate and number of apnea events should be displayed on 
  the GUI.  The breathing rate and number of apnea events displayed on the GUI
  should be updated each time new data is obtained as above (i.e. at least every
  five seconds).
+ If the number of apnea events is two or greater, that value should be 
  displayed in red.  If the number of apnea events is zero or one, it should be 
  displayed in the default color of the rest of the text in the GUI.
+ Every 60 seconds, the most recent values for breathing rate, number of
  apnea events, and CPAP pressure should be sent to the server to
  be stored in the current patient record.
+ While data acquisition is in progress, the user should be able to change
  the entered CPAP pressure (again, validating that it remains in the 4 to 25
  range).  The user can then submit this new pressure to be stored on the
  server as the most recent CPAP pressure.  This new pressure should
  also be sent to the MockCPAP class so that the patient breathing can respond
  accordingly.
+ At any time flow vs. time data is visible in the GUI, the user should have
  the ability to upload a snapshot of the current flow vs. time plot to the
  server to be stored in the patient's record.
+ The user should have the ability to stop data acquisition.  When this 
  happens, further updates to the flow vs. time data should stop, but the
  latest data should remain visible in the GUI.  The server should
  be notified that data acquisition has been stopped but the patient is still
  in the room.
+ After data acquisition is stopped, the user should have the ability to
  restart data acquisition for the same patient.  Upon restart, the currently
  visible flow vs. time data should be removed.  The displayed BPM and number
  of apnea events removed, and new data obtained starting at time=0.  A new
  MockCPAP instance should be created to simulate starting over.
+ The user should have the ability to reset the GUI.  This reset should stop
  any ongoing data acquisition.  All patient data should be removed from the GUI.
  The room number, patient MRN, and patient name entries should be cleared and
  reactivated so new information can be added.  Any data about the previous
  patient should be removed so it is not accidentally uploaded with any new
  patient information.  The server should be notified that the patient
  is no longer in the room.  The GUI should then be ready for a completely new 
  patient.
+ The user should have the ability to quit the GUI causing the program to stop.
+ The GUI should periodically (at least every 30 seconds, but can be more 
  frequent) query the server
  to see if a new CPAP pressure has been commanded by the monitoring station.
  If so, the value in the CPAP pressure entry should be automatically updated
  to that new value.  This new value should then be sent to the MockCPAP instance
  for any impact on patient breathing.    
  *NOTE: after this monitoring-station commanded CPAP pressure change, if the 
  user on the patient-side changes the CPAP pressure entry to a different value, 
  the CPAP pressure  
  must NOT be changed back to the value commanded from the monitoring station 
  unless a new command from the monitoring station is received.*
+ The GUI should provide appropriate user feedback to indicate the success or
  failure of actions.  In other words, if an action is taken by the user, there
  must be some indication of a change in the GUI or direct feedback to the user.


### Monitoring-Station GUI Client
The monitoring-station GUI will be considered a stand-in for a central 
monitoring location where the sleep lab technicians can monitor the CPAP 
results for all patients and command changes in the CPAP pressure for specific
patients/rooms.

At a minimum, your monitoring-station GUI client should provide a __graphical__
user interface with the following functionality:
+ Make RESTful API requests to the server to get lists of active room
  numbers, patient information, available patient data, and any other
  information as needed by the specifications below.
+ Allow the user to see, in a single display, the following information for each
  room that has an active patient:
  + The room number
  + The patient MRN
  + The patient name
  + The latest CPAP pressure
  + The latest value for breathing rate
  + The latest value for number of apnea events
+ If the number of apnea events is two or greater, it should be displayed in red.
  If the apnea count value is zero or one, it should be displayed in the 
  default text color used by the rest of the GUI.
+ The interface should make periodic requests to the server (at least every 30 seconds, but
  can be more frequent) for updated information and the GUI should be updated 
  with this latest information.  
+ When data acquisition for a patient is stopped, the values for CPAP pressure,
  breathing rate, and number of apnea events should be indicated as 0, "--" or 
  some other way to show that the CPAP is not running.
+ When the patient leaves the room (as indicated by the patient-side GUI being
  reset or quit), all information about that room and patient should be 
  removed from the GUI.
+ If a new room/patient is started and added to the server, the information for
  that room/patient should be added to the GUI.
+ The user should be able to select an active room.  For this selected room,
  the user should be able to do the following:
  + see a plot of the number of apnea events vs. CPAP pressure for all data 
    available for that patient.  This plot should indicate the name and MRN
    of the patient.
  + to be able to select and display an available snapshot for that patient
    based on the timestamps of the snapshots
  + when either of the above plots is displayed, the ability to save the plot
    to a file on their computer with a location and filename of their choosing
  + if a plot of the number of apnea events vs. CPAP pressure is being actively
    displayed, it should be automatically updated with any new data that
    becomes available on the server (as discovered in the periodic requests to
    the server).
  + Allow the user to enter an updated CPAP pressure and upload this new
    pressure to the server to be retrieved by the patient-side GUI.  The GUI
    should only allow integer values of 4 to 25, inclusive, to be entered and uploaded.
  + When the user wants to select a different snapshot to display, the 
    choices presented should represent the 
    most recent options on the server.  In other words, the options for choices
    must dynamically update, rather than be "locked in" based on what was 
    available when the client was started.  The options should update
    automatically without the user needing to click a button or take any
    other action other than making a new selection.
+ When the user is done looking at data from a particular room, they should
  have the ability to make that information go away and select another room.

### Cloud Server
At a minimum, your server should be a cloud-based web service running on your 
virtual machine that exposes a well-crafted RESTful API that will implement 
the tasks needed by the clients as described above and outlined here:

* Communicate with and utilize a persistent database that will store any
uploaded data for retrieval at a future time.
* Accept uploads from the patient-side client that will include a room number,
patient medical record number (MRN), patient name, and latest CPAP pressure.
* If the upload contains an MRN that does not exist in the database, a new
  patient record should be created in the database.  If the upload contains an
  MRN that does exist in the database, the patient information for that MRN
  should be updated in the database as needed.  (Note, the patient name could
  be updated as well).
* Accept a data point upload for a particular MRN.  This data point upload
  will consist of a breathing rate and number of apnea events.  These two
  pieces of data should be stored in the patient record, along with the date and 
  time of receipt of this data.
* Accept requests from the monitoring-station client to retrieve the following
information from the database and download it to the client:
  + a list of room numbers which currently have active patients
  + the name and medical record number of the patient in a specific room
  + the latest CPAP pressure, breathing rate, and number of apnea events for 
    the patient in a specific room
  + historical apnea event vs pressure data for the patient in a specific room
  + a list of snapshot timestamps for the patient in a specific room
  + a specific snapshot based on timestamp for the patient in a specific
    room 
  + any other information that may be required by the monitoring-station client
  
  __Note__: The above list does not imply that you must have one route for
  each of those items.  Just make sure your server provides the needed 
  services.
* Accepts requests from the monitoring-station client with updated CPAP
pressure information for a specific room
* Accepts requests from the patient-side client with updated CPAP pressure as
  commanded from the patient-side client
* Accepts requests from the patient-side client for any new CPAP pressures
  commanded by the monitoring-side client, 
* Provide any other services as needed for either client to perform its needed
functions.

**Note**: The GUIs should only make requests to the server and should not make 
contact with the database.  All database functions should be handled from the
server.  If the GUI needs to interact with the database, it should do it by
making requests of the server. 

### Multiple Patient-side Clients
The system should allow for multiple patient-side GUIs to be running 
simultaneously to simulate a sleep lab where multiple CPAPs are reporting to
a central monitoring station.  In theory, you should not need to make any
coding adjustments based on whether there is only a single patient-side client
running or multiple patient-side clients running.  I will be
testing your final submission by opening up multiple patient-side GUIs and a 
single monitoring station GUI and using all at the same time.  You may want to
test your system that way at least once.

## Choice of GUI Framework
`tkinter` can provide all of the GUI functionality necessary to meet the
above objectives.  However, you are also welcome to use a different GUI
framework if you like, such as PyQT or any other choice.  You are also welcome
to program a web/browser GUI for your clients if you prefer.  Visit
<https://github.com/dward2/BME547/tree/main/Resources/WebInterface> for info
and basic tutorials for using HTML/CSS/flask to create such an interface.  Note
that this web/browser GUI should be implemented by its own server (i.e., its
own `flask` based code) that makes requests to the separate cloud server as
described above.  The cloud server should not have its own interface.

## Database
Using MongoDB and `pymongo` will satisfy the requirements
for a persistent database.  As all team members will be working with the 
database, the use of any other type of persistent database (SQL instead of
non-relational, or a non-MongoDB online option) requires approval from all
team members and the instructor.

**Patients and Room**

Initially, each room and patient that is created will be new. When a patient
is done in a room, it is possible that the room number will be reused.  And, it
is possible that a patient will come back into the lab and either use the same
room number or be put into a different room.  When a patient comes back,
additional data should be added to their existing database entry.

During my testing of your code, I will ensure that I never assign multiple
patients to the same room at the same time.  So, your code does not need to
check or validate against that possibility.

There is no theoretical limit to the number of rooms which might be created and
used.  So, you cannot assume an upper limit.
